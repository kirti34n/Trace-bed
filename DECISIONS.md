## D-001 Rename: Strata → Tracebed
**Decision:** The service, package, schema, and CLI are named `tracebed`. **Context:** "Strata" collides with Palo Alto Networks' Strata security product family (sold to this exact SOC/BFSI buyer) and Strata Identity (strata.io), which ships identity orchestration for AI agents; both `strata` package names are squatted (PyPI, npm). **Alternatives:** Moraine, Patina (runners-up; PyPI collisions or weaker fit). **Rationale:** Tracebed names the architectural thesis ("layered memory over a trace bed"; nothing is remembered that doesn't stand on a trace) and has a clean sweep: PyPI, npm, GitHub org all free. **Date 2026-07-25.**

## D-002 Postgres 18, not 16/17
**Decision:** Target PostgreSQL 18. **Context:** Spec §12 said 16/17; PG18 went GA 2025-09-25, ten months before the spec's own datestamp. **Alternatives:** PG16 (one line from the back of the support window), PG17. **Rationale:** pg_textsearch requires PG17+; PG18's async I/O directly benefits a disk-resident HNSW index — the exact hot-path failure mode; greenfield services should not start near EOL. **Date 2026-07-25.**

## D-003 Lexical default: pg_textsearch (true BM25, PostgreSQL License); ts_rank demoted
**Decision:** BM25 via TigerData's `pg_textsearch` is the lexical default; native `ts_rank` becomes a zero-extension fallback only. **Context:** BEIR SciFact nDCG@10: ts_rank **0.07**, BM25 0.69, pgvector 0.66, RRF hybrid 0.70 — fusion does not rescue ts_rank, it grants a 0.07 ranker equal reciprocal-rank weight. Decisive second reason: §7.5's rarity gate ("≥2 rare terms") **is** an IDF computation and ts_rank has no IDF — the abstention gate's signal source would not exist. **Alternatives:** ParadeDB pg_search (AGPL-3.0, stays listed as opt-in), ts_rank default (refuted). **Rationale:** True BM25 under the PostgreSQL License removes AGPL from the lexical slot entirely — a strict win for the license invariant. Caveat recorded: pg_textsearch is young (v1.x, 2026). **Date 2026-07-25.**

## D-004 Python 3.13 minimum
**Decision:** Python 3.13 (GIL build; do not chase free-threading). **Context:** Prompt rule 10 pinned 3.12, which has been security-fix-only since ~April 2025. **Alternatives:** 3.12 (stale), 3.14 target later. **Rationale:** Greenfield service on a maintained branch; the dependency set (FastAPI, Pydantic v2, psycopg 3) all support 3.13. **Date 2026-07-25.**

## D-005 License policy: allowlist + denylist; LGPL-3.0 permitted for dynamically-linked unmodified libraries
**Decision:** Allow PostgreSQL / Apache-2.0 / BSD / MIT / ISC, **plus LGPL-3.0-only for unmodified, dynamically-linked libraries with recorded rationale**. Hard denylist: SSPL, BSL, RSAL, Elastic-v2. AGPL only behind driver interfaces as opt-in, never default. **Context:** psycopg 3 — mandated by the same prompt whose rule 9 allowlist excludes it — is LGPL-3.0-only; the CI license gate would fail on commit one. **Alternatives:** swap to asyncpg (Apache-2.0); ban LGPL. **Rationale:** LGPL is not viral across process/link boundaries for an unmodified library; psycopg 3 is the better-supported driver for this design. Recorded LGPL dependency: **psycopg 3 (LGPL-3.0-only, used unmodified, dynamically linked)**. **Date 2026-07-25.**

## D-006 MinIO demoted to legacy compatibility only
**Decision:** Trace-archive S3 targets are SeaweedFS (Apache-2.0) and the filesystem driver; MinIO is "legacy compatibility with an existing deployment only — not for new installs." **Context:** MinIO's OSS repo was archived 2026-04-25; unmaintained, source-only, admin console previously stripped. **Alternatives:** keep MinIO as listed opt-in (misleading). **Rationale:** The S3 driver speaks generic S3 (no MinIO SDK), so legacy MinIO still works without endorsing it. Side-finding forwarded to the Atom owner: Atom's compliance bucket pins the now-frozen `minio/minio:latest`. **Date 2026-07-25.**

## D-007 Embedding pin: Gemini `gemini-embedding-2`, halfvec, ≤768 dims, stamped per row
**Decision:** Default embeddings (indexing **and** query) are Gemini `gemini-embedding-2` behind `EmbeddingPort`; model id + version + dimension stamped on every `memory_item` row; `halfvec(768)`. A pinned local ONNX driver is a fully supported secondary for air-gapped/latency-sensitive deployments. Re-embedding is an explicit versioned migration (new `embedding_model` row + backfill job); mixed-model retrieval is refused. **Context:** Nothing in the spec pinned the embedding model; a silent swap invalidates the entire vault — the same argument the spec itself makes for pinning judges. **Alternatives:** local-only ONNX default (worse accuracy; kept as secondary), caller-supplied vectors (pushes model deps into every runtime). **Rationale:** Human decision: accuracy beats latency. **Date 2026-07-25.**

## D-008 Worker generation: Gemini 3.1 Pro default via OpenAI-compatible interface; §13 privacy claim rewritten; scoring epochs
**Decision:** Contribution judge, shadow validator, and distiller default to **Gemini 3.1 Pro** (Flash configurable per worker) through an OpenAI-compatible `LLMProviderPort` (Google direct / LiteLLM / gateway = one config line). §13's "run content never leaves the deployment" is rewritten: query and trace content leaving the deployment is **accepted** in the default profile; the local ONNX embedding driver plus a local OpenAI-compatible endpoint is the documented answer for customers who refuse. A `scoring_epoch` (judge model id/version, sampling params, prompt hash) is stamped on every scored artifact; cross-epoch comparison is rejected. **Context:** The judge and validator gate Q and promotion — errors there corrupt the vault permanently; the spec's "local vLLM" mandate had no hardware floor and no epoch concept. **Alternatives:** pinned local open-weight models as default (kept as a profile); "vLLM-compatible" wording (needlessly narrow). **Rationale:** Human decision: accuracy beats latency/locality for the vault-gating workers. **Date 2026-07-25.**

## D-009 rrf_k = 60 in typed config, with per-arm weights
**Decision:** `retrieval.rrf_k = 60`, `rrf_weight_vector = rrf_weight_lexical = 1.0`, all typed config. **Context:** §14 omitted rrf_k entirely — a magic number by construction under rule 12. **Rationale:** Standard RRF constant; per-arm weights exist because unweighted RRF over unequal-quality arms measurably underperforms. **Date 2026-07-25.**

## D-010 Latency budget relaxed: 300ms p99 total, 200ms query-embed timeout, explicit degradation ladder
**Decision:** Total retrieval budget 300ms p99; query-embed sub-budget 200ms. Embed timeout → lexical-only; total budget exceeded → static prefix only; store error → nothing. Fail-open throughout. **Context:** The original 100ms p99 was unmeetable with a remote query embedding, and the audit showed the single-project warm bench certified a condition production never has. **Alternatives:** 100ms with local-only embedding (worse accuracy); no budget (unbounded). **Rationale:** Human decision: accuracy beats latency; the ladder keeps every failure mode fail-open and *observable* (`retrieval_event.outcome_code`). The bench becomes 50 projects × 100k, concurrent, and is informational (not CI-gating) until the human flips it. **Date 2026-07-25.**

## D-011 Q-update formula corrected: weight scales the learning rate, not the reward
**Decision:** `Q ← clamp01(Q + α·w·c·(r − Q))` with `r` = outcome polarity ∈ [0,1] from the adapter, `w` = adapter trust weight, `w = 0` short-circuits. Tie-break for the one-update-per-day cap: highest-w adapter, then earliest arrival; idempotent under replay via `outcome_event.event_id`. **Context:** Spec §9 fed the adapter weight in as the reward `r`: with Q starting at 0.5, a *successful* downstream event (weight 0.3) yields `r − Q = −0.2` and **lowers** the score — the update punishes success; implicit signals (0.0) would drive Q to zero, the exact guessed-reward failure invariant 4 forbids. **Alternatives:** none viable; the spec formula is arithmetically wrong. **Rationale:** The weight expresses how much the signal is trusted, not how good the outcome was. **Date 2026-07-25.**

## D-012 Phase 2 vault gate restated as a trend assertion; quarantine/candidate TTLs added
**Decision:** The Phase 2 gate asserts *net vault growth rate strictly decreasing across the soak, with a projected plateau date* — not an observed plateau. Quarantine TTL 30d, unpromoted-candidate TTL 45d (→ archived). **Context:** Decaying 5%/idle-week from 0.5 to the 0.15 floor takes ln(0.3)/ln(0.95) ≈ 23.5 weeks ≈ **164 days** against a 30-day soak — arithmetically unpassable; separately, quarantined and candidate rows had no exit, so no state had a bounded population. **Alternatives:** lengthen soak to ~180 days (slow), raise decay to ~15%/wk (changes semantics). **Rationale:** The trend assertion is measurable in 30 days and is what the metric actually needs to show. **Date 2026-07-25.**

## D-013 One state machine (spec §8 diagram and §12 enum reconciled)
**Decision:** Single status enum: `quarantined, candidate, validated, superseded, stale, retired, archived, pinned, tombstoned`; Trace/Extracted are not memory states; Tier A/B live in immutable `trust_tier`; the full legal/illegal transition table in PLAN.md §5 is the source of truth for table-driven tests. `archived → validated` (operator restore) exists; retirement from `validated` requires the principal threshold (D-021). **Context:** The spec's diagram and enum were two different machines; the mandated transition tests could not be written. **Date 2026-07-25.**

## D-014 Preferences and derived state: `pinned` status / separate table (SM-05)
**Decision:** Preferences live in `memory_item` with explicit ungoverned status `pinned` (operator provenance; only edges creation→pinned, pinned→tombstoned). Derived state moves to its own `derived_state` table outside the state machine (versioned deterministic overwrite is a different shape). **Context:** Both types had no legal initial status; "deterministic overwrite" is exactly what the machine forbids for governed rows. **Alternatives:** ungoverned flag on governed statuses (muddies the transition table). **Date 2026-07-25.**

## D-015 RRF orders; abstention thresholds calibrated raw signals
**Decision:** RRF (k=60) is used only to order the fused candidate list. The abstention decision thresholds **calibrated raw signals**: cosine similarity and saturation-normalized BM25 (`s/(s+k)`), plus the rarity gate computed from pg_textsearch per-project IDF (cold start: abstain below 200 corpus docs). The composite ranking score uses the calibrated signals, never RRF output. **Context:** Spec §7.3 fused with RRF then §7.4–7.5 thresholded a composite with a 0.40 similarity term — but RRF discards score magnitudes by construction; its output encodes consensus rank, not relevance, and a rank cannot be thresholded for "good enough to inject." **Date 2026-07-25.**

## D-016 Dynamic memory block placed last, after all cacheable content
**Decision:** `context_block.placement = "append_last"`. The static prefix (definition, pinned preferences, validated agent-type lessons) stays in the cacheable region; the dynamic block always renders after all cacheable content. **Context:** Provider prompt caching invalidates a changed block *and everything after it*; a dynamic block between the cached prefix and the conversation invalidates everything downstream on every run — destroying the prompt-cache economics the prefix builder exists to create. **Date 2026-07-25.**

## D-017 Isolation stack: server-derived project_id + typed repository + forced RLS + LIST partitions with a ceiling
**Decision:** (1) `project_id` derived server-side from the authenticated principal via `agent_registration` — never caller-asserted; (2) typed repository where every builder requires a `ProjectId` newtype, no scope-less constructor exists, and an AST lint bans raw SQL outside `stores/pg/`; (3) RLS with `FORCE ROW LEVEL SECURITY` on every partitioned table as backstop; (4) LIST partitioning as a lifecycle mechanism (O(1) project deletion) with a documented ceiling of **1,000 projects per instance** and a stated migration path to HASH partitioning behind the same repo API. Rule 6 restated: the wall covers **every key in every store** (Postgres, Valkey, trace store, exports), not just queries/sweeps/indexes. **Context:** The host (Atom) has no project entity and defaults to an unverified actor header; caller-asserted scope makes construction-layer partitioning security theatre; production leak reports concentrate on by-id routes, not search. **Date 2026-07-25.**

## D-018 The service mints run_id and returns it from retrieve()
**Decision:** `run_id` is a UUIDv7 minted server-side at `retrieve()` and returned; the SDK echoes it on `trace`/`feedback`/`propose_memory`. Runs that never call retrieve: SDK mints locally, flagged `origin=sdk`. **Context:** The host has no per-invocation identifier for standalone agents; without run_id every join in credit assignment breaks. This makes credit assignment work with zero host support. **Date 2026-07-25.**

## D-019 Tier A notes are template + enum, zero byte passthrough
**Decision:** Tier A operational notes are rendered exclusively from closed-vocabulary templates (error-class enums, tool ids, hashes, numeric fields); no byte of tool output, stderr, or validator text enters a note; raw text stays in the trace behind a pointer. Gate test: no substring ≥8 bytes from a tool error body appears in any note. **Context:** "No free text flows into the note" was false: tool error bodies echo attacker input, tracebacks quote payloads, and Pydantic v2 embeds the offending value as `input_value=` in validation errors — the "structured" note carried attacker text verbatim into same-run injectable candidates. **Alternatives:** keep free text with Tier B quarantine for Tier A (loses the immediacy that justifies Tier A). **Date 2026-07-25.**

## D-020 Corroboration requires computable independence; skip ships disabled
**Decision:** `trace_index` gains `submitter_principal` and `input_signature_hash` in Phase 0. Independence = **differing authenticated principal AND differing input-signature cluster** (64-bit SimHash, Hamming ≤ 8 = same cluster). The "2+ independent traces" shadow-validation skip ships **disabled** until both columns exist and Phase 3 enables it with this definition. `propose_memory` proposals are a provenance class that can never satisfy any skip (D-023). **Context:** From the spec's schema, "independent" was uncomputable (only run_id existed), so the skip degraded to "submitted twice" — a two-call Sybil bypass. GovMem (arXiv:2607.02579) measured naive count-based corroboration at a **0.597 false-promotion rate**; Tracebed's traces are maximally correlated by construction. **Date 2026-07-25.**

## D-021 outcome_event carries an authenticated principal; retirement needs K distinct principals
**Decision:** Every outcome_event records the authenticated `principal_id`. Automatic retirement (Q < 0.25 after ≥4 scored uses) additionally requires outcomes from ≥ **K = 3** distinct principals; below K, the memory routes to the review queue instead. **Context:** The Q arithmetic was a memory-destruction primitive: with c≈1, r=0 from 0.5: 0.35 → 0.245 → 0.172 → 0.120 — four scored uses, exactly the retirement precondition, at one update/day = **four calendar days** for a single attacker-controlled feedback source to retire any memory. **Date 2026-07-25.**

## D-022 Derived state gets controls: rate-bounded movement, clamp alert, divergence alarm
**Decision:** Baseline movement per update is clamped to ±10%; a clamp binding 3 consecutive updates raises an alert; a slow (30d) vs fast (24h) reference divergence >25% raises an alarm. Guardrail-flagged runs are excluded from baseline contribution. **Context:** Derived state had zero controls by design and was assigned to watchdogs — textbook boiling-frog baseline poisoning, with a successfully walked baseline reading as *positive* lift to the kill switch. This intentionally makes derived state no longer "zero gating." **Date 2026-07-25.**

## D-023 propose_memory is a provenance class that satisfies no skip, plus rate caps
**Decision:** Proposals land quarantined with `provenance.class="proposal"`; that class can never satisfy the corroboration skip or the human-verdict skip. Caps: 2 proposals/run, 50/project/day. **Context:** Proposals arrive as traces, so two proposals = two traces = the corroboration skip — agent_control had a direct two-call route to validated with attacker-chosen wording (including the exact rare-term trigger). **Date 2026-07-25.**

## D-024 Shared scan suite moves to Phase 0; inserts require proof-of-scan
**Decision:** The injection-pattern/secret/schema scan suite is a Phase 0 shared module (`core/scans`); the repository rejects any `memory_item` insert without a `ScanVerdict`. Phase 2's gate adds "seeded injection in a tool error body never reaches candidate." **Context:** The spec sequenced the scans inside the Phase 3 distiller while Tier A shipped injectable in Phase 2 — an entire phase (with a sign-off in the middle) of unscanned attacker-shaped strings entering context. Honest coverage note recorded: injection-pattern scans measure ~42–60% TPR on weak-signal memory poisoning; the scan is a cheap layer, never the reason anything is trusted. **Date 2026-07-25.**

## D-025 Erasure via per-subject crypto-shredding; trace_subject side table
**Decision:** Trace payload sections attributable to a subject are envelope-encrypted under a per-subject KEK (`subject_key`); erasure = KEK destruction, tombstoning content while the stored object stays byte-immutable and provenance pointers stay intact. `trace_subject(run_id, project_id, subject_tag)` (multi-valued) makes subjects findable. Built in Phase 0 — it cannot be retrofitted onto a plaintext archive. **Context:** The trace was simultaneously the erasure target and the audit record (incompatible as specified), trace_index had no subject column (subjects literally unfindable), and the flagship host stores audit objects under a 90-day COMPLIANCE object lock no one can bypass. **Date 2026-07-25.**

## D-026 Render-as-data reclassified: governance control, not security control
**Decision:** Keep the invariant, the exact header, and the property tests (template-only rendering); **remove render-as-data from the anti-poisoning control list**. **Context:** Delimiting is the weakest spotlighting variant — ~50% ASR reduction non-adaptive, >95% ASR under adaptive attack (Hines et al. arXiv:2403.14720; Nasr et al.). It preserves policy subordination; it does not stop a designed adversary and must not be cited as if it does. **Date 2026-07-25.**

## D-027 Kill-switch lift is stratified; arm assignment logged on the trace
**Decision:** Lift is computed on runs where something was actually injected, versus a shadow-retrieved holdout (the holdout arm runs the retriever and discards the result, so comparable runs are identifiable). Trigger: conservative lower confidence bound < 0 sustained 14 days, per-cell minimum N = 200, Benjamini–Hochberg correction. Arm assignment: salted deterministic hash, session-stable, never disables working memory or the tool cache, recorded on `trace_index.arm`. **Context:** With ≥50% abstention, aggregate on-vs-off lift is mostly noise-vs-noise; 5% split across agent-type × mem-type cells collapses N; uncorrected 95% CIs fire on ~1 cell in 20 per window by chance. **Date 2026-07-25.**

## D-028 Positioning: three novelty claims retracted with prior-art citations; no LoCoMo-derived evidence
**Decision:** §2's claims are corrected as follows. **Claim 1 (governed promotion — "nobody ships this"): refuted** — GovMem (arXiv:2607.02579) and MemClaw / Governed Shared Memory (arXiv:2606.24535) ship governed promotion/scoped writes; cite as prior art. **Claim 8 (trace-up consolidation): refuted** — Eywa (arXiv:2605.30771) preserves provenance chains to raw data to prevent recursive-summary degradation; ACE (arXiv:2510.04618, ICLR 2026) names "context collapse"; keep the invariant, drop the novelty claim. **Claim 7 (subject tags): refuted as novelty** — the data subject is a first-class Contextual Integrity parameter and CIMemories (ICLR 2026) benchmarks it; reframe as "first implementation in an agent memory store." **Claim 6 (derived state as a distinct write class) holds.** Surviving differentiators: outcome-grounded promotion between named organisational scopes, the adapter-conditioned quality lane, and the earn-your-context kill switch. **LoCoMo-derived numbers are inadmissible as evidence** — a 2026 audit found 99 score-corrupting errors in 1,540 questions and its judge accepted 62.81% of deliberately wrong answers. **Date 2026-07-25.**

## D-029 Auth: OIDC (Keycloak-compatible) + API-key mode; the service verifies its own credentials
**Decision:** Two first-class auth modes: OIDC bearer verified against a configurable JWKS (Keycloak-compatible), and hashed API keys. No unverified-header mode exists. Verdict-skip, corroboration, and operator edits are unavailable to unverified principals by construction (there are none). **Context:** The flagship host defaults to a self-asserted, unverified actor header; the human-verdict skip at weight 1.0 was otherwise forgeable by any caller who could reach the port. **Date 2026-07-25.**

## D-032 "Correction" split: correction_adapter (0.8) vs operator_edit (1.0)
**Decision:** Two mechanisms, two names. `correction_adapter` (w = 0.8): inferred signal from a human editing the agent's *output*; flows through the scorer. `operator_edit`: a human editing a *memory* on the dashboard; not an adapter, bypasses the scorer, supersedes directly (a state-machine transition). **Context:** The spec used one word at two weights (0.8 in §9, 1.0 in §15), producing divergent Q trajectories per implementer. **Date 2026-07-25.**

## D-033 SDK durability contract
**Decision:** Fire-and-forget through a local ring buffer with periodic flush; drop-oldest at capacity with a loss counter; per-run monotonic sequence numbers; a `run_end` sentinel; traces with gaps or no sentinel are marked `outcome_status='incomplete'` and the distiller refuses them. Accepted loss window: buffer contents on process crash. **Context:** "Fire-and-forget" and "every run produces a complete trace" cannot both hold without a stated contract; deriving lessons from silently truncated traces produces wrong lessons with formally complete provenance. **Date 2026-07-25.**

## D-034 Migration tool: yoyo-migrations (plain SQL)
**Decision:** `yoyo-migrations` (Apache-2.0), plain-SQL migrations, plus a first-party partition manager that applies the current schema to partitions created after the migration ran. **Alternatives:** Alembic (drags SQLAlchemy against the lean-deps rule), first-party runner (reinventing ordering/locking). **Rationale:** Partitioned DDL is cleanest in raw SQL; one small dependency. **Date 2026-07-25.**

The five phase STOPs remain non-negotiable. **Context:** Human decision to trade ceremony for velocity where the risk is low. **Date 2026-07-25.**

**Decision:** "Memory is an enhancer, never a dependency" is scoped to *learned* memory (the retrieval path). ## D-039 Phase 0 module names reconciled to the contract; no re-export shims
**Decision:** `src/tracebed/stores/pg/models.py` -> `rows.py` and `src/tracebed/api/routes.py` -> `routes_v1.py`, renamed to the names PHASE0-CONTRACT.md §1/§5.2/§9.3 already gave them; `api/models.py`, `ingest/runner.py` and `stores/valkey/client.py` added to the §1 module map; §13.2's test-file map rewritten to the tree as built (ten of its rows named files nobody wrote — the subject matter had been merged into differently-named modules). **Context:** Four of six parallel chunks independently reported the same two name mismatches as merge blockers; a consumer following the contract literally would have failed at import. **Alternatives:** re-exporting shims at the contract names (rejected — two importable names for one module guarantees the next reader picks the wrong one, and the drift survives); amending the contract to the built names (rejected — the contract is what later work is planned against, and `routes_v1` also carries the versioning the API will need). **Rationale:** Renaming is mechanical and fully covered by the suite; a map naming files nobody wrote is worse than no map, because a reader cannot distinguish "not written" from "written elsewhere". **Date 2026-07-25.**

## D-040 `POST /admin/agents/register` is one registry transaction, not three composed calls
**Decision:** `Repo.create_agent_registration(project_id, agent_type_name, principal_kind, external_ref, key_hash)` performs the agent_type upsert, the principal insert and the agent_registration insert inside one transaction, and `AdminPort` declares that method **instead of** `create_agent_type`/`create_principal`/`register_agent`. **Context:** The route composed three independent `Repo` calls, each with its own transaction. A `DuplicateRegistration` on the third committed an orphan `agent_type` and an orphan `api_key` principal whose `key_hash` was live but whose plaintext had been returned to nobody — an undead credential deposited by every failed retry of a retryable admin call. The FK chain forces the write order, so no reordering fixes it. **Alternatives:** compensating deletes in the route (rejected — a compensation that can itself fail is not atomicity, and it runs in a different transaction from the write it undoes); keeping the three builders on `AdminPort` and documenting the hazard (rejected — an atomic implementation reachable only by convention is not atomic). **Rationale:** The registry tables are unpartitioned and share one connection path, so a single transaction is available and cheap; declaring only the atomic method on the Protocol makes the non-atomic composition unreachable from a route rather than merely discouraged. The agent_type half is `ON CONFLICT (project_id, name) DO UPDATE ... RETURNING`, which also makes §9.3's "creates agent_type if new" true rather than aspirational. **Date 2026-07-25.**

## D-041 `POST /v1/invalidation` persists synchronously; it does not get a fourth queue topic
**Decision:** The route writes one `invalidation_event` row through `Repo.insert_invalidation_event(project_id, event_type, selector)`, scoped by the authenticated principal's `ProjectScope`; `event_id` is server-generated. **Context:** PLAN.md §3 lists the route and PLAN.md §5 defines the table, but PHASE0-CONTRACT.md §9.3's route table lists neither, so the route shipped authenticating, resolving scope, returning 202 "accepted" and discarding the body — the one failure mode a 202 must never have, because "accepted" and "accepted and stored" are indistinguishable from the wire and every future integration test would have passed by accident. **Alternatives:** a fourth queue topic (rejected — §14's queue DO-NOT list forbids adding topics beyond the three constants); leaving the route a documented stub (rejected — a lie that passes tests is worse than a missing route). **Rationale:** §14's "routes 202 + enqueue — do NOT write synchronously" names trace and outcome rows, the two high-volume tables; an invalidation is a small bounded row on a low-rate webhook path, so a scoped insert is within both the letter and the intent. **Date 2026-07-25.**

## D-042 Concurrent trace-index writers serialise on a per-run advisory lock
**Decision:** `ScopedRepo.get_trace_index(run_id, *, for_update=False)`; `ingest.trace_writer` always passes `True`, which takes `pg_advisory_xact_lock` on the (project_id, run_id) pair and then `SELECT ... FOR UPDATE`. **Context:** The trace-index upsert replaces `path` wholesale — jsonb cannot be per-key merged by `ON CONFLICT` — so the writer's read-modify-write of `seq_ranges`/`payload_refs` is unsafe under concurrency. Two workers holding different batches of one run each read the pre-batch `path` and the last commit wins: a lost range can pin a complete run at `incomplete`, and a lost `payload_refs` entry orphans the only pointer to that batch's ciphertext. **Alternatives:** `FOR UPDATE` alone (insufficient — it locks nothing when the row does not exist yet, which is exactly the first-batch race); a jsonb per-key merging upsert (a larger change to frozen SQL, and it would still not order the two writers' reads); routing all batches for a run to one consumer (a partitioning scheme Phase 0 has no mechanism for). **Rationale:** The advisory lock covers both the existing-row and the not-yet-existing case, is transaction-scoped so there is no unlock path to forget, and is keyed per run so it does not serialise unrelated ingest. `for_update` defaults to `False` so plain reads stay lock-free. **Date 2026-07-25.**

## D-048 Abstention signals must be finite; the cosine domain is [-1, 1], not [0, 1]
**Decision:** `hotpath/abstention.py` and `hotpath/calibration.py` refuse non-finite raw signals at construction (`CandidateSignals.bm25_raw`, `CandidateSignals.cos_sim`, `CalibratedSignals`' four terms, `bm25_saturate`'s `raw_bm25`/`k`, `recency_weight`'s `age_days`/`half_life_days`), and `cos_sim` is accepted over `[-1, 1]` rather than `[0, 1]`. **Context:** Two defects, opposite in direction. (a) FAIL OPEN: every gate is a `<` comparison, NaN compares `False` against everything, and `bm25_raw` was validated with `self.bm25_raw < 0` — which NaN and `+inf` both pass. `bm25_saturate(nan)` and `bm25_saturate(inf)` both return NaN, so `bm25_norm < bm25_norm_threshold` was `False` and a candidate whose lexical score was a store overflow or a null INJECTED, having cleared every threshold gate; verified against the pre-fix code, `decide()` returned `inject=True, outcome_code=None` for both. (b) FAIL CLOSED: the vector arm computes `1 - (embedding <=> query)` over pgvector cosine ops, whose range is `[-1, 1]`, so a candidate pointing away from the query raised `ValueError` inside the hot path. `Pipeline` catches everything from the retrieval stage and reports `store_error`, so an ordinary abstention would have been recorded as the system failing — the exact confusion `retrieval_event.outcome_code` exists to prevent (PLAN.md §5). **Alternatives:** clamping NaN to 0.0 and injecting nothing silently (rejected — a NaN out of a store is the system failing, and the ladder already has a rung that says so; swallowing it hides the store defect forever); clamping a negative cosine to 0.0 (rejected — it is a real signal and gate 2 already rejects it correctly, so clamping would only destroy the distinction between "weakly related" and "opposed"). **Rationale:** Every range check is written `not (lo <= x <= hi)` rather than `x < lo or x > hi` precisely so NaN falls on the refusing side; `math.isfinite` covers the one-sided bounds. `bm25_saturate`'s documented codomain is corrected from `[0, 1)` to `[0, 1]`: the real-valued function never reaches 1, but `raw + k == raw` in binary floating point past roughly `k * 2**53`, so `bm25_saturate(1e308, k=10.0)` is exactly 1.0 — harmless (such a score should pass) but the old docstring's claim was false and the test only checked up to 1e6. **Date 2026-07-26.**

## D-056 Assembler/renderer audit: `total_tokens` is the outer bound; an empty assembly renders nothing; non-finite scores are refused
**Decision:** Four behavioural changes to the `assembler-renderer` chunk, each made because the previous behaviour was wrong rather than merely unspecified.
(a) **`budget.total_tokens` clamps every pool.** `assemble()` now derives its static pool as `min(budget.static_prefix, budget.total_tokens)` and its dynamic pool as `min(budget.dynamic, budget.total_tokens - static_used)`. Previously the two section budgets were spent independently and an `AssertionError` — commented "structurally unreachable" — guarded the sum. It was reachable: `budget.*` is per-project and per-agent-type overridable (`OVERRIDABLE_SECTIONS`) and nothing validates that `static_prefix + dynamic <= total_tokens`, so an operator lowering only `total_tokens` got a `500` out of the hot path instead of a smaller block.
(b) **`render([])` returns `rendered=""`, not a lone `MEMORY_HEADER`.** `Pipeline._ladder` calls `render(assembled.slots)` on the abstention and empty-result rungs too, where the slot list is empty. A bare header is not "nothing" (PLAN.md §2 invariant 2): it spends prompt tokens telling the model memory was recalled when none was — the exact false-confidence signal abstention exists to suppress — and it diverged from `domain.events.empty_context_block()`, which the degradation rungs of the same function already use with `rendered=""`.
(c) **`ContextBlock.slots` carries the rendered order.** `render()` regrouped into `SLOT_ORDER` for `rendered` but stored the caller's raw order in `slots`. `injection_log.slot` rows come from `slots` while the model saw `rendered`; an auditor reconstructing the prompt from the structured view would have reported an order the prompt never contained.
(d) **`Candidate.__post_init__` refuses a non-finite `score`.** NaN compares `False` against everything, so `sorted(key=(-score, memory_id))` stops being a total order: measured, one NaN among three candidates produced four distinct packings depending only on the retriever's iteration order, breaking the module's stated determinism and the reproducibility of a rendered block from its stored `retrieval_event`. Mirrors D-048's identical refusal one layer up in `hotpath/abstention.py`.
Two defensive additions with no behaviour change under the shipped defaults: `SLOT_ORDER` is checked at import time for totality over `Slot` and for duplicates (it drives both `renderer._render_text` and `assembler._DYNAMIC_SLOTS`, so a member missing from it was a memory item silently never rendered *and* never reported as dropped), and `budget.slot_caps` is read with `.get(slot.value, 0)` because a project override may legally replace the whole mapping and omit a slot — a `KeyError` there would be an unhandled failure on a path invariant 2 requires to degrade, not fail.
**Context:** `dropped_memory_ids` is now derived by subtracting the selected set from the input set rather than accumulated inside `_dedup`/`_pack`, which is what makes (a)'s and the `slot_caps` case's exclusions observable instead of silent — an accumulate-as-you-go scheme reports nothing at all for a candidate that never reaches a `_pack` call.
**Alternatives:** validating `static_prefix + dynamic == total_tokens` in `BudgetConfig` (rejected — `domain/config.py` is outside this chunk's file list; clamping at the consumer is the fix available here and is correct regardless); clamping a NaN score to `0.0` (rejected — same reasoning as D-048: a NaN out of the scorer is the system failing, and swallowing it hides that forever).
**Rationale:** Every one of these is covered by a test that goes red under the exact mutation it exists to prevent; the mutations were run and the reds observed, not assumed. **Date 2026-07-26.**

## D-057 Retriever audit: the purity gate's last violation is fixed at its root, `fused_top_n` is applied, and invariant 7 is enforced on the way out
**Decision:** Five changes to the `retriever` chunk (`hotpath/retriever.py`, `hotpath/fusion.py`, `stores/pg/search.py`), each because the previous behaviour was wrong, not merely unspecified.
(a) **`hotpath/retriever.py` no longer imports `adapters.ports`.** It declares a local, `@runtime_checkable` `QueryEmbedderPort` Protocol carrying exactly the one `embed()` method it calls. This was the single remaining `purity_check.py` violation in the whole tree (`hotpath.retriever -> adapters.ports -> adapters.identity`), and D-055 correctly identified it as this file's to fix: `adapters/ports.py` and `scripts/purity_check.py` are both outside this chunk's file list, so the fix available here is to not create the edge. Invariant 1 is CI-blocking from this phase; a gate that fails is not a gate. `tests/phase1/test_retriever.py::test_local_query_embedder_port_matches_the_real_embedding_port` compares `inspect.signature` of the local and real `embed` so the copy cannot drift. The underlying contract_gap stands and is reported: `purity_check.py`'s `imports_of()` should skip nodes nested under `if TYPE_CHECKING:`, since those imports never execute and therefore cannot reach a generative client at runtime.
(b) **`retrieval.fused_top_n` is applied.** It was a live field of `RetrievalConfig` (PLAN.md §6, default 20) that no code in the repository read: fusion returned the entire union of both arms, up to `2 * arm_top_n` (100) candidates, straight into the assembler. `retrieve()` now cuts the fused list to `cfg.fused_top_n`, clamped at zero so a non-positive override cannot become a negative slice bound — which would mean "all but the last |n|", the exact opposite of a cap. `candidates_considered` deliberately still reports the full pre-fusion union (contract §5.2 measures work done, not survivors).
(c) **The lexical arm is submitted BEFORE the embed call, not after.** `embed_timeout_ms` (200) is two thirds of `total_budget_ms` (300), so an embed that runs to its timeout with the lexical arm not yet started spent 200ms and only then began the one arm still able to answer: the `degraded_lexical` rung would routinely blow the total budget and be demoted a second time by the ladder to `timeout_prefix_only`. Overlapping the two pays the lexical query's latency inside the embed window. Proven by a test whose fake embedder refuses to return until the lexical arm has actually started.
(d) **`stores/pg/search._row_to_arm_hit` enforces the retrievability predicate on returned rows.** Every other guarantee in that module is a property of query TEXT; a future edit (a new arm, a UNION, a hand-written variant missing one conjunct) can change it with no test noticing until a quarantined row is in a prompt. A row that is not `validated`, or a `candidate` row not at Tier A, now raises `TracebedError` instead of becoming an `ArmHit` — the message carries ids and enum values only, never `content`. Failing closed costs one retrieval (the ladder's store-error rung; invariant 2 is preserved, the run does not fail); failing open costs the entire quarantine guarantee. `_RETRIEVABLE_STATUS_VALUES` is the single source of truth for both the bound query parameter and this check, so the query and its post-condition cannot disagree.
(e) **`document_frequency` bounds its term list (`_MAX_DF_TERMS`, 512).** `terms` is derived from caller-supplied query text and its sibling `top_n` was already clamped; unbounded, one pathological query becomes an unbounded `text[]` parameter and an unbounded server-side `unnest`. Truncation rather than refusal because the rarity gate needs only `abstention.rarity_min_shared_terms` (2) rare shared terms — dropping the tail of an absurd term list can only make the gate stricter, never flip an abstain into an inject. Same class of bound as `_MAX_ARM_TOP_N`: a DoS ceiling, never a retrieval-quality tunable, and reported as a contract_gap rather than treated as a config value.
**Also fixed:** `tests/phase1/test_fusion.py::test_smaller_rrf_k_amplifies_a_rank_one_advantage` could not fail — it recomputed the RRF formula by hand and only asserted that `fuse()` returned something, so it stayed green against a `fuse()` that ignored `rrf_k` entirely (verified by running the original test body against exactly that mutant). Replaced with a test asserting `fuse()`'s own output ORDER across the `k=2` crossover of `1/(k+1) = 2/(k+4)`, where a rank-1-in-one-arm candidate and a rank-4-in-both-arms candidate genuinely swap places between `rrf_k=1` and `rrf_k=60`.
**Alternatives:** applying `fused_top_n` in the assembler instead (rejected — the assembler would then do per-candidate content fetch and tokenisation for up to 100 rows before cutting to 20, which is the cost the knob exists to avoid); making the retrievability check a `logger.warning` (rejected — invariant 7 has no "log and continue" mode); editing `adapters/ports.py` or `scripts/purity_check.py` to fix (a) at its true root (rejected — hard rule 6, neither is in this chunk's file list).
**Rationale:** every change above is covered by a test that was observed going red under the exact mutation it exists to prevent — the cut removed, the clamp removed, the submit reordered, the guard deleted, the predicate's `OR` turned into `AND`, `scoped()` swapped for a bare connection, the term bound dropped, and `rrf_k` hardcoded. **Date 2026-07-26.**

## D-058 The retrieval deadline is anchored at call entry, and the embed sub-budget is clamped to what remains of it
**Decision:** `hotpath.budget.Deadline` accepts an explicit `started_at_ms` anchor, and `hotpath.pipeline.Pipeline` passes the `clock.monotonic_ms()` reading it took on entry to `retrieve()`; `Pipeline._embed_bounded` then narrows `retrieval.embed_timeout_ms` to `min(embed_timeout_ms, remaining)` before handing the config to the retriever. **Context:** the audited implementation constructed the `Deadline` inside `_run_ladder`, i.e. AFTER config resolution and holdout assignment. Two consequences, both real: (a) `ConfigResolver.effective()` reads `project_config` / `agent_type_config`, so it can stall — and a stall there was excluded from the very budget it blew, so a 350ms config stall produced a full search and an `outcome_code=injected` row with a >300ms wall time; (b) the ladder's first `total_exceeded()` check (before the retriever) was provably dead code, since elapsed time at ladder entry was always 0 and the constructor rejects a non-positive budget. The embed clamp is the same defect one level down: PLAN.md §6's two budgets are nested, not independent, so an embed call handed its full 200ms with 40ms of the total left overruns the budget the caller is actually waiting on, detectable only afterwards. **Alternatives:** leaving the anchor and treating the pre-ladder latency as negligible (rejected — it is a store round trip, which is exactly the thing that stalls); passing a remaining-time float into `Retriever.retrieve()` as a new parameter (rejected — `retriever.py` is another chunk's file, and `RetrievalConfig` already carries the field, so `model_copy` narrows it with no signature change anywhere). **Rationale:** invariant 2's budget is the *call's* budget. Both numbers still come from `EffectiveConfig`; the clamp only ever narrows, and it is reached only after `total_exceeded()` was false, so the clamped value is at least 1ms and can never reach `EmbeddingPort.embed` as a degenerate `timeout_ms=0`. Proven by mutation: reverting the anchor, ignoring the supplied anchor, removing the clamp, and widening `Deadline.total_exceeded()` by one tick each turn a test red. **Date 2026-07-26.**

## D-059 `Pipeline.retrieve()` takes no `agent_type_id`: it is read from the server-derived `ProjectScope`
**Decision:** the `agent_type_id` parameter is removed from `Pipeline.retrieve()`, from `CandidateAssemblyPort.run()`, and from `StaticPrefixPort.get()`; all three read `scope.agent_type_id`. **Context:** `/v1/retrieve`'s request body carries `agent_type: str` (PLAN.md §3), while the authoritative agent type comes from the `agent_registration` row `Repo.resolve_project()` reads (`UNIQUE(principal_id)` — one principal resolves to exactly one agent type). A pipeline that accepts an agent_type_id alongside the scope is a channel for the caller-asserted one to arrive: agent-type-scoped memories, the per-agent-type static prefix key, and the per-agent-type config overlay would all be selectable by whatever the caller wrote in the body. **Alternatives:** keeping the parameter and asserting it equals `scope.agent_type_id` (rejected — a check that exists only when someone remembers to call it, versus a channel that does not exist at all); keeping it for symmetry with `scope` (rejected — that symmetry IS the defect). **Rationale:** invariant 4 says scope is derived server-side and never caller-asserted, and `routes_v1.py` already applies that one dimension in — `_trace_envelope` stamps `str(scope.agent_type_id)`, never `body.agent_type`. This makes the hot path match. **Date 2026-07-26.**

## D-060 A session-less run is its own session; `assign_arm` refuses an empty session key
**Decision:** `Pipeline.retrieve(..., session_id: str | None = None)` substitutes the minted `run_id` when `session_id` is absent or blank, and `holdout.assign_arm` raises on an empty `session_key`. **Context:** the audited signature required `session_id: str`, but the wire field is `api.models.RunCtxIn.session_id: str | None = None`, so the wiring step would have had to pass `None` or a placeholder. Hashing a shared placeholder puts EVERY session-less run of one agent_type into a single draw: at `killswitch.holdout_pct = 5` that is a 5% chance that 100% of that traffic sits in the holdout arm (memory withheld wholesale once Phase 3 acts on the assignment) and a 95% chance that none of it does (lift measured on an empty cell). **Alternatives:** deriving a key from `run_ctx.user_ref` (rejected — optional, and conflates "who" with "which session"); leaving `session_id` required and pushing the choice onto the route (rejected — that is how the placeholder gets invented, silently, downstream). **Rationale:** a run with no session is its own session: still deterministic for that run, still uniform across runs, and D-027's session-stability claim is unaffected because there is no session to be stable across. The `assign_arm` guard makes the degenerate input loud instead of plausible. **Date 2026-07-26.**

## D-061 `retrieve()` guards the clock, the run-id mint, and the response-model construction, not only its dependencies
**Decision:** `Pipeline` wraps `clock.monotonic_ms()`, `clock.now_ms()`-seeded run-id minting, the latency read, and the `RetrieveResult` construction, and type-checks the `StaticPrefixPort` return value before it reaches the response model. A monotonic-clock failure degrades to `store_error` (nothing can be budgeted, and unbudgeted work on the synchronous path is what invariant 2 forbids); a wall-clock failure falls back to `ids.uuid7`'s own time source. **Context:** the audited implementation guarded every dependency call but left four statements outside every `try`. The reachable one: `StaticPrefixPort` has no implementation until Phase 2's `prefix_builder`, so its return value is unvalidated data read back out of Valkey — `_timeout_prefix_only` caught the *call* raising but not the *value* being wrong, and a wrong-typed value reaches the Pydantic response model from outside every ladder guard. `Clock` is likewise an injected Protocol, i.e. third-party code on the hot path. **Alternatives:** one outer `try` around the whole method (rejected — it would swallow the outcome the ladder had already computed and report `store_error` for a call that had genuinely retrieved something); trusting the prefix port's declared return type (rejected — that is the definition of unvalidated). **Rationale:** "a run never blocks or fails because of Tracebed" is a claim about `retrieve()`'s boundary, not about its dependencies' boundaries. The one boundary this class still does not own is `mint_run_id()` failing outright (`os.urandom` failing), which is exactly what `run_id_origin="sdk"` exists for (D-018 / C-26). Proven by mutation: removing each guard, and trusting the prefix value, each turn a test red — including a case where the prefix returns a mapping that relabels the block, which Pydantic would otherwise coerce and which invariant 3 forbids. **Date 2026-07-26.**

## D-063 `/v1/retrieve` calls the real `Pipeline` only when `AppDeps` supplies one; `AppDeps` cannot be extended from this chunk's file list

## D-064 `scripts/purity_check.py` skips `if TYPE_CHECKING:` bodies
**Decision:** The purity gate's AST walk no longer counts imports nested under `if TYPE_CHECKING:` (or `typing.TYPE_CHECKING`) as reachability edges; the `else:` branch of such a guard, and every function-local import, still count. Two new self-test assertions pin both halves. **Context:** `adapters/ports.py` names `adapters.identity.Principal` under that guard purely for an annotation. `adapters.ports` is on the gate's `ALLOWED_INTERNAL` list and `adapters.identity` is not, so the walk reported `hotpath.X -> adapters.ports -> adapters.identity` as a violation for an import that never executes. Four Phase 1 modules independently declared duplicate local Protocols to route around it (D-055, D-057, and `hotpath/pipeline.py`'s `TelemetryRecorderPort`/`RetrievalOutcomeLike`), producing the strange steady state where NO hot-path module could import the one adapters module the gate explicitly permits. The gate was green only because everyone had routed around it. **Alternatives:** adding `tracebed.adapters.identity` to `ALLOWED_INTERNAL` (rejected — it widens the allowlist for a module the hot path genuinely must not reach at runtime, trading a false positive for a real hole); moving `Principal` into `domain/` (rejected — it is an authentication type with an adapters-shaped lifecycle, and relocating frozen Phase 0 surface to satisfy a linter is the tail wagging the dog); leaving it (rejected — a gate that is red for a reason no edit to the audited package can fix stops being read, and invariant 1 is CI-blocking from this phase). **Rationale:** A `TYPE_CHECKING` import emits no runtime import, so it cannot reach a generative client; counting it is a strictly false edge. The narrow recogniser (bare `TYPE_CHECKING` / `x.TYPE_CHECKING` only) keeps any unfamiliar guard being walked, because over-approximating reachability is a false red and under-approximating it is a hole — only one of those is safe to get wrong. The duplicate Protocols were left in place with corrected docstrings: each now stands on the reason that outlives the false positive (a narrower surface for offline fakes), and each has a signature-drift test. **Date 2026-07-26.**

## D-065 A gate whose arm produced no signal is SKIPPED, not failed
**Decision:** `abstention.CandidateSignals.cos_sim` and `.bm25_raw` are `float | None`; `decide()` skips the cosine gate when there is no cosine and the BM25 gate when there is no BM25, and refuses a candidate carrying neither. `AbstentionDecision.bm25_norm` is correspondingly `float | None`. The rarity gate is unaffected — it reads no arm score, so it applies in full on every rung. **Context:** `hotpath.fusion.FusedCandidate` carries `ArmSignal | None` per arm ("a candidate absent from an arm carries None rather than a zero score — zero is a real score"), but `CandidateSignals` required a `float` for both. The abstention chunk flagged this as the one modelling question it would not decide unilaterally, because the two readings have opposite consequences and neither is a measurement. **Alternatives:** absent ⇒ that gate fails (rejected — on the ladder's `degraded_lexical` rung NO candidate has a cosine, because the vector arm never ran, so a rung PLAN.md §2 defines as a WORKING degradation would return nothing on every call forever, while every dashboard showed a healthy service); absent ⇒ substitute 0.0 (rejected — silently abstains everything, same failure with a number attached); absent ⇒ substitute 1.0 (rejected — silently injects on evidence nobody gathered). **Rationale:** A gate is a test applied to evidence; with no evidence there is nothing to test. This does mean a lexical-only candidate is not cosine-checked — that is the honest cost of the degraded rung, and it is bounded: the rarity gate (the strongest of the three, and the one that stops a generic query matching generic memory) plus the arm that DID answer still apply. Separately, `calibration` still needs a number for its similarity term, and there 0.0 is used deliberately — as the additive identity of that term, documented at the call site — because the score's job is to ORDER candidates against each other and re-normalising weights per-candidate would put two candidates in one list on two different rulers. **Date 2026-07-26.**

## D-066 `hotpath.assembly` tokenises with its own word splitter, not pg_textsearch's
**Decision:** "Shared term" is computed by a pure `[0-9a-z]+` splitter applied to both the query and the candidate's content; per-term document frequency is still computed by the server (`content @@@ term`) under the real tokenizer. **Context:** The rarity gate needs the query terms a candidate actually shares, which requires tokenising candidate content — and pg_textsearch's tokenizer (stemming, stopwords, its `text_config='english'`) is not reachable from a pure function on the hot path. **Alternatives:** a per-candidate `to_tsvector` round trip (rejected — one statement per candidate on a 300ms budget, which is the shape the whole assembly design exists to avoid); shipping a Python stemmer (rejected — a new dependency, and D-036 keeps the dependency set closed). **Rationale:** The two tokenizers disagree only on inflection, and the disagreement is one-directional: a query term and a candidate term differing only by suffix are NOT counted as shared here even though the index would match them, so the gate sees fewer rare shared terms than a stemming tokenizer would. `rarity_min_shared_terms` is a `>=` bar, so undercounting can only turn an inject into an abstain — never the reverse. The df numbers themselves stay authoritative because the server computes them. **Date 2026-07-26.**

## D-067 The score's validity term is the row's stored `confidence`
**Decision:** `CalibratedSignals.validity` is filled from `memory_item.confidence`. **Context:** `calibration.py` documents validity as "a validity term in [0, 1] (e.g. lower for a Tier-A `candidate` row than for `validated`) — computed upstream", and PLAN.md §6's `score.*` section has `w_validity` but no field from which a per-status or per-tier validity could be derived. **Alternatives:** a status/tier table in code (rejected — every entry would be a literal threshold `domain/config.py` does not define, which is hard rule 4's exact prohibition); inventing `score.validity_validated` / `validity_candidate` config fields (rejected — inventing config surface is the same violation one layer up, and PLAN.md §6 is the authority on what fields exist). **Rationale:** `confidence` is already a per-row `[0, 1]` number whose whole purpose is "how much do we believe this", it needs no new surface, and it moves with the row rather than with a static table. Reported as a contract gap: if the intent was for validity to encode trust tier or status, PLAN.md §6 needs the fields, and `hotpath/assembly.py` is the one call site to change. **Date 2026-07-26.**

## D-068 `injection_log` is written by the pipeline, from rows the assembly produces
**Decision:** `hotpath.assembly.CandidateAssembly` returns `stores.pg.rows.InjectionRow` objects for the memories that actually reached a slot, and `Pipeline` writes them through a new optional `InjectionRecorderPort` (satisfied structurally by the existing `stores.pg.telemetry.Telemetry.record_injections`). The port is optional and its call is individually guarded: a deployment with no `injection_log` writer degrades to no forensics, never to a failed retrieve (invariant 2). **Date 2026-07-26.**

**Decision:** `Pipeline._run_ladder` re-checks `deadline.total_exceeded()` after `CandidateAssemblyPort.run` returns, degrading to `timeout_prefix_only`. **Context:** The ladder checked the budget before the retriever and after it. `hotpath.assembly` then issues three more store round trips of its own — candidate content, per-term document frequency, corpus size — which neither earlier check could have covered, because that work did not exist yet. **Alternatives:** passing the deadline into `CandidateAssemblyPort.run` so it could pre-empt itself (rejected for now — it widens a seam every fake implements, and the honest pre-emption it would enable needs a `statement_timeout` derived from the remaining deadline, which is a `stores.pg` change; recorded as remaining work instead). **Rationale:** Without the third check a call answers `injected` at 400ms while writing a `retrieval_event` that says the budget held — the latency histogram that is supposed to correct `total_budget_ms` would be reading its own blind spot. ## D-070 Invariant 7 is re-asserted on the last hop before the renderer
**Decision:** `stores.pg.search`'s retrievability post-condition is exported as `assert_dynamically_retrievable(memory_id, status, trust_tier)` and called a third time by `hotpath.assembly`, on every fetched row, before it can become an `assembler.Candidate`. **Context:** The SQL predicate is the control; `_row_to_arm_hit` and `_row_to_candidate` assert it held for rows THIS module produced. ## D-075 derived-state audit: the slow reference is the far end of the retained history, not a 30-day mean; a guardrail-flagged reading contributes nothing; `DerivedConfig` is refused where it is consumed
**Decision:** Six changes to the `derived-state` chunk (`workers/baselines.py`, `workers/derived_state.py`), each because the previous behaviour was wrong rather than merely unspecified.
(a) **The slow reference is the earliest reading still inside `SLOW_WINDOW`, not the mean of that window.** The audited implementation computed both references as per-sample means, which measures the drift RATE and not the cumulative displacement the config names. Measured, one reading per day: a 9 %/day walk alarmed on day 6, a 2 %/day walk on day 24, and a **1 %/day walk never alarmed at all** — a trailing mean is computed over the attacked series, lags a geometric walk by roughly half the window, and so has an emergent floor of ~1.6 %/day (≈60 % per 30 days) that nobody chose, against a knob that says 25 %. Anchored on the earliest retained reading the same three walks alarm on days 3, 12 and 23, and the undetectable steady-state drift becomes exactly `divergence_alarm_pct` per `SLOW_WINDOW` (~0.74 %/day). The residual floor is intrinsic and is now pinned by a test (`test_the_detection_floor_is_pinned_not_assumed`) instead of being discovered from an incident. The anchor is also unmoveable by volume: a per-sample mean lets whoever schedules the writer pick the detector's sensitivity (100 readings in one day outvote 29 days of history), and update frequency is a scheduling detail, never a security parameter.
(b) **The alarm compares the slow reference against the value just written as well as against the fast (24h) reference, and reports the larger.** The fast reference is a mean, so three clamp-legal +10 % steps inside one window park the stored baseline 33 % above the reference while the window's own mean is only 21 % above it — and `derived_state`'s consumers read the latest row's `value`, not a mean. With at most one update per fast window the two comparisons are identical, so this adds no false positives for a normally-scheduled writer.
(c) **`DerivedStateUpdateResult.divergence_evaluated` distinguishes "the watchdog found nothing" from "the watchdog could not answer".** A key whose whole history is one instant has nothing to compare against; reporting that as a silent `divergence_alarm=None` is how a blind watchdog looks like a healthy one.
(d) **Both watchdogs are seeded from the store on the first touch of a key** (`DerivedStateStorePort.recent_versions` replaces `latest_version`; one read serves the rate bound, the reference history and the clamp streak, so two reads of the same rows cannot disagree). The reading history and the clamp streak previously lived only in process memory: a restart made the slow reference the first reading written *after* it — i.e. wherever the baseline had already been walked to, forgiving every unit of accumulated drift — and restarted the clamp streak at zero. A deploy did that for free. Measured against the unfixed code, an adaptive attacker writing 12 times a day walked the baseline **2.85x inside the first 24 hours** and was then permanently ahead.
(e) **`guardrail_flagged` (was `excluded_from_reference`) drops the reading entirely.** D-022 says guardrail-flagged runs are "excluded from baseline contribution"; the audited implementation still applied the value to the baseline and only hid it from the divergence windows — the exact inverse, a suspect run moving the stored baseline while being invisible to the one watchdog that could have noticed. No version row is written, the reference history does not see it, the clamp streak does not move.
(f) **`DerivedStateWriter.__init__` refuses a degenerate `DerivedConfig`.** `derived` is an `OVERRIDABLE_SECTION` and none of its four fields carries a pydantic constraint, so all of these arrive from a `project_config` row. `keep_versions: 0` is the dangerous one: it prunes away the row the rate bound reads, so every update looks like a first write and **nothing is ever clamped** — the movement clamp silently removed by a retention knob, with every dashboard still showing a clamp configured. Also refused: a non-positive `baseline_max_delta_pct` (freezes or inverts the bound), `clamp_alert_consecutive < 1` (alerts on every clamp), a negative `divergence_alarm_pct` (alarms always).
**Also fixed:** windows are half-open `(now - window, now]` (closed at both ends, one reading per day put 31 readings in a "30 day" window and two days in a "24 hour" one); a clock that moves backwards is refused, since every window here is measured as "how long ago" and the reference is chosen by age; the rate bound reads the highest-version row rather than the last element of the store's sequence; and the `_clamp_alert_active` latch is now covered by a test that first drives a streak far enough to set it (the existing reset test stopped at two clamps, so a latch that was never cleared survived it).
**Alternatives considered:** weighting each 24-hour period equally instead of anchoring on one reading (implemented and measured — it fixes volume-dragging but not the warm-up hole, and lets the far end of the window be reshaped by whatever landed in its last period; the adaptive attacker still reached 2,935 vs the anchor's 156 over 40 days); adding `derived.slow_window_days` / `fast_window_hours` / `max_updates_per_period` config fields (rejected — hard rule 4 makes an absent field a contract_gap, not a licence to invent one; `SLOW_WINDOW`/`FAST_WINDOW` stay `Final` module constants of this control); putting the config constraints in `domain/config.py` where D-071 put the retrieval ones (rejected — outside this chunk's file list; refusing where the value is consumed is the fix available here and is correct regardless).
**Rationale:** every change above is covered by a test that was observed going red under the exact mutation it exists to prevent — sixteen mutations run (slow reference reverted to a 30-day mean, the value comparison removed, each window boundary closed, the clamp comparison flipped, each of the three config thresholds hardcoded to its default, the guardrail drop removed, seeding removed, the alert latch left uncleared, the backwards-clock guard removed, the `keep_versions` refusal removed, `delta_pct` zeroed, the non-finite refusal removed, `divergence_evaluated` pinned True), zero survivors. **Date 2026-07-26.**

## D-076 The Phase 2 kill switch acts on every injection path, not only on JIT
**Decision:** `hotpath.assembly.killswitched(mem_type, cfg)` is the one definition of "this memory type is disabled", exported and used by both `CandidateAssembly.run` (every `/v1/retrieve`) and `hotpath.jit.JitGate`. A killswitched row is skipped before the abstention gate and is not reported as an abstention.
**Context:** integration grep showed `killswitch_overlay` was read by exactly one module in the whole tree, `hotpath/jit.py`. The shared function is asserted to be the same object from both modules by test, so the two paths cannot diverge silently. ## D-077 A Tier A lane coordinator owns the per-run candidate cap and batch idempotency
**Decision:** `workers/tier_a_lane.py` (`TierALane`) is the single caller of the four Tier A extractors. It constructs exactly one `CandidateCapTracker` per batch and threads it through all four in a fixed order, and it interposes a deduplicating `MemoryWriterPort` that hashes rendered content with `domain.canonical.content_hash` and returns the existing row's id instead of inserting when the project already holds that content. `TierALaneResult.dedupe_is_durable` reports whether the cross-batch half of that guarantee is actually available.
**Context:** the extractors chunk made the shared tracker POSSIBLE (an optional `cap_tracker` parameter) but nothing constructed one, so `tier_a.candidate_cap_per_run = 1` behaved as a cap of 4 in any real deployment. Separately, `Repo.insert_memory_item` is a plain INSERT against a `memory_item` table whose only constraint is `PRIMARY KEY (project_id, id)`, while `queue.lease_seconds`/`max_attempts` make work-item redelivery ordinary -- so a redelivered extraction batch re-inserted every candidate, straight into the metric Phase 2's soak gate measures.
**Alternatives:** a unique index on `(project_id, content_hash)` (correct, and still the structural fix -- rejected here because it is a migration against Phase 0's frozen DDL and there is no Postgres on this machine to verify it against, so it would ship unexecuted); filtering duplicates out of `outcomes` after extraction (rejected -- `emit_candidate` reserves the cap slot BEFORE it renders and scans, so a post-filter lets an already-stored note spend a run's one candidate slot and starve a genuinely new sibling); raising from the writer on a duplicate (rejected -- `emit_candidate` treats any writer exception as fatal to the batch, so one known note would destroy every new note behind it).
**Rationale:** both defects are properties of the lane rather than of any parser, which is why four correct per-extractor suites could not see either. Extractor order is fixed and asserted because the cap is first-come: a lane whose order varied would charge a different note against the same run's one slot from machine to machine, and the soak's vault-growth curve would stop being reproducible. Ten mutations, including restoring the per-extractor tracker, were each applied and each turned the suite red. **Date 2026-07-26.**

## D-078 `NoveltyGate.decide` takes a `project_id` and refuses a foreign-project signature
**Decision:** `ExistingSignature` carries `project_id`, `NoveltyGate.decide` takes one, and any candidate whose project differs raises `TracebedError` -- refusing the whole call rather than skipping the row.
**Context:** `structural_signature` hashes (error_class, tool_id, tool_version, payload_class_hash) and nothing in it names a project, so two projects running the same tool produce byte-equal signatures. The gate was a pure function over signatures with no project anywhere in its types, so a store query that lost its scope would be told to merge, and `merge_provenance` would graft one project's trace_ids onto the other project's memory -- invariant 4 broken through a function that could never have refused. ## D-079 A current-version pointer key makes the static prefix cache readable
**Decision:** `stores.valkey.keys.current_prefix_version_key(project_id, agent_type_id)` -- `tb:{project_id}:pxcur:{agent_type_id}` -- holds the live `prefix_version`, with `ValkeyClient.current_prefix_version_get/_set` around it. `PrefixBuilder.run` publishes the block first and repoints the pointer second.
**Context:** `prefix_version` is derived from the packed content, and `hotpath.pipeline.StaticPrefixPort.get(scope)` receives only (project_id, agent_type_id, principal_id); a content-derived version is by construction not computable by a reader that does not already hold the content, and `ValkeyClient` exposes no pattern scan. The prefix builder was therefore correct, deterministic, and completely unreachable.
**Alternatives:** a `prefix_version` column on a registry row (rejected -- a Postgres round trip on the degradation ladder's prefix-only rung, which exists precisely because Postgres is slow or down); a version that is a pure function of (project_id, agent_type_id) (rejected -- it destroys the "identical input set yields an identical version" property the whole cache rests on, since the key would no longer change when the content did); widening the `px:` value to hold both pointer and block (rejected -- the versioned key stays immutable and content-addressed, so two readers resolving the same version can never disagree about the bytes, and a rebuild leaves the previous block readable for requests already in flight).
**Rationale:** publish order is the safety property. A pointer written first names bytes that are not in the cache yet, so every reader in that interval takes a hard miss on the one rung that exists to avoid one; block-then-pointer means the worst intermediate state is a pointer still naming the previous version, stale but complete. A pointer whose stored bytes are not a plain non-negative decimal reads as a miss rather than raising, because `int()` would accept `" 7"`, `"+7"` and `"1_0"` as versions no writer ever published. The key shares the `tb:{project_id}:` prefix, so `delete_project`, `cache_flush` and leak probe 6 cover it with no change. **Date 2026-07-26.**

## D-080 Degenerate `derived`/`lifecycle`/`scoring`/`queue` overrides die at the config layer, and `q_start` must sit above `archive_floor`
**Decision:** `DerivedConfig`, `LifecycleConfig`, `ScoringConfig` and `QueueConfig` carry pydantic field constraints, and `EffectiveConfig` gains a cross-section validator refusing `scoring.q_start <= lifecycle.archive_floor`. `ConfigResolver.effective` translates the resulting `ValidationError` into `ConfigError` so one exception type still means "this project's config rows do not make sense". `DerivedStateWriter` keeps its own refusal as defence in depth, tested against a `model_construct`-ed config the field constraints never saw.

## D-082 The obvious SQL fix for lease-stealing `nack()` is unsound and was NOT applied
**Decision:** `_NACK_SQL` stays `UPDATE work_queue SET available_at = now() + %(backoff)s, lease_expires_at = NULL WHERE id = %(id)s`. The lease-overrun defence stays where the runner chunk put it: client-side in `WorkerRunner`, which declines to nack a batch whose own claim lease has elapsed and counts `WORKER_LEASE_OVERRUNS`.
**Context:** `nack()` clears `lease_expires_at` with no ownership check, so a consumer that outran its lease can hand a row away from whichever consumer has since claimed it. The natural store-side fix is to add `AND lease_expires_at > now()` to the WHERE clause.
**Alternatives:** that clause (rejected -- it is backwards. If the lease merely expired and nobody reclaimed the row, `lease_expires_at` is in the past and the guarded nack becomes a no-op, losing the backoff for the SAFE case. If another consumer has since reclaimed the row, `lease_expires_at` is that consumer's FUTURE timestamp, so the predicate is true and the theft proceeds. The guard refuses exactly the harmless case and permits the harmful one); a lease-holder token column (correct, and the real fix -- a migration against Phase 0's frozen DDL plus a `renew` primitive on `QueueConsumerPort`, neither verifiable without a Postgres).
**Rationale:** recorded because the wrong fix is more obvious than the right one, and shipping SQL that cannot be executed on this machine would have made a correctness claim nothing checked. Until a lease token exists, `attempts`/`max_attempts` still bound the retry budget, so the residual cost of an unguarded overrun is a lost backoff interval and possible duplicate processing -- which is why every consumer behind `QueueConsumerPort` is required to be idempotent in the first place. **Date 2026-07-26.**

## D-083 `scoring.updates_per_memory_per_day` gains a floor of 1 and deliberately no ceiling
**Decision:** `ScoringConfig.updates_per_memory_per_day` becomes `Field(default=1, ge=1)`. No upper bound is added, and `tests/phase3/test_learning_loop_seams.py::test_the_daily_scoring_cap_still_has_no_upper_bound` pins that absence so whoever closes it must record the number they chose.
**Context:** `scoring` is an `OVERRIDABLE_SECTIONS` member, so a `project_config` jsonb row reaches this field, and it was the one scoring-adjacent value in the module with no constraint at all (`alpha` is `gt=0, le=1`, `q_start` is `ge=0, le=1`, and D-080 constrained the rest of the section). Unlike `promotion`/`retirement`/`lifecycle` it is NOT projected into `TransitionLimits`, so the invariant floors added there do not cover it and nothing downstream floors it either — `run_scorer_batch` honours whatever it is given. Verified by construction: `ScoringConfig(updates_per_memory_per_day=1000)` and `=-5` were both accepted before this change.

Upward is the genuinely dangerous direction — the daily cap is what bounds how fast a single feedback source can walk a memory's Q, and D-021 sizes its four-calendar-day retirement window on this being 1 — but PLAN.md §6 gives the field a default and no range, so the ceiling is a human's call, not an integrator's. ## D-084 Forensic containment of a poisoned `validated` memory is reversible, and that is recorded rather than fixed

## D-087 The proposal caps become a durable, cross-process control; the in-process lock is demoted to a pre-check
**Decision:** `stores.pg.repo.Repo` gains `insert_proposal_within_caps`, which runs the redelivery check, the per-run cap, the per-project-per-UTC-day cap and the `memory_item` INSERT inside ONE transaction holding a project-scoped `pg_advisory_xact_lock(PROPOSAL_CAP_LOCK_CLASS, hashtext(project_id::text))`. `workflow.agent_control.AgentControl` calls it whenever the injected store satisfies the new optional `DurableProposalCapPort`, and that result — not the in-process count — is authoritative. The three read-only queries `AgentControlRepoPort` declared (`count_proposals_in_run`, `count_proposals_in_project_day`, `find_proposal_in_run`) are implemented on `Repo` at the same time, so the port is satisfied by the shipped store rather than by fixtures only. `AgentControl.durable_caps` reports which guarantee is in force, and `workers.runner.run()` refuses to start a proposal consumer wired to a store that cannot give the durable one.
**Context:** Phase 4 landed the caps behind `AgentControl._cap_lock`, a `threading.Lock`. That makes them exact for every submission ONE process handles and was correctly recorded by the builder as a contract gap: two API/worker processes sharing one Postgres each observe `count == cap - 1` and each insert, so the real bound was `cap x concurrent processes`. `proposals.per_run_cap` / `per_project_daily_cap` are the only control that stops an agent flooding its own vault with self-authored beliefs (PLAN.md §6), so a control that holds only in the single-consumer deployment is a control that stops holding exactly when the fleet grows.
**Alternatives:** (a) `INSERT ... SELECT ... WHERE (SELECT count(*) ...) < cap` — one statement, no lock, but the sub-select and the insert are not mutually exclusive under READ COMMITTED, so it has the identical race in SQL rather than in Python. (b) A partial unique index — enforces a fixed cap, not a configurable one, and `per_run_cap` is an `EffectiveConfig` field a project can override. (c) `SELECT ... FOR UPDATE` on the existing proposals — there is no row to lock when the count is zero, which is precisely the case that must be serialised. (d) `SERIALIZABLE` for this transaction — would work, but turns a cap refusal into a serialisation failure the caller must retry, on a path that already has an at-least-once queue behind it.
**Rationale:** An advisory lock is the one mechanism that serialises a COUNT. It is transaction-scoped, so it is released by COMMIT or ROLLBACK with no unlock path to forget, and contention is bounded by the very control it protects (50 proposals/project/day). The in-process pre-check is kept, not deleted: it refuses an over-cap proposal before it pays for the scan suite, and it is explicitly documented as an optimisation that never decides the outcome. The day bounds are computed in Python as an explicit half-open UTC range rather than `DATE(created_at)`, because `DATE()` on a `timestamptz` renders in the session's `TimeZone` and would have made a per-UTC-day cap silently become a per-server-local-day cap.
**Date 2026-07-26.**

## D-091 Project-scoped cache flushing is composed, not remembered
**Decision:** `workflow.prefetch` gains `combined_project_flush(*flushes)` and `PrefetchingRetriever.project_flusher()`. **Context:** An adversarial re-read of the chunk asked what a vector landing on the wrong row would look like now that the ANN arm has rows at all. Row-to-vector *pairing* was already correct (`validate_batch` fixes the count, `zip(..., strict=True)` fixes the order). The reachable failure was one level up: the worker took `pin` and `embedding_port` as two independent constructor fields and never compared them, while being the only code in the tree that writes `embedding_model_id`/`embedding_model_version`. Step 2 of `adapters/embedding/pinning.py`'s own documented migration -- "deploy with `EmbeddingConfig` pointing at the new pin" -- performed without redeploying the driver therefore stamps every row with the NEW pin over the OLD model's vector. Nothing downstream can detect it: `assert_pin_matches` compares a row's stamp against the configured pin and they agree, and the re-embed predicate treats the row as done, so it is never revisited. That is "swap the embedding model silently" (PLAN.md section 10) reached by an ordinary-looking config change. Separately, nothing restricted the sweep to retrievable rows, so quarantined and tombstoned content would receive vectors; `stores.pg.search.vector_arm`'s status predicate is the only thing that then keeps them out of a prompt.

(b) Raise a local `ValueError` with a driver-specific message instead of delegating to `assert_pin_matches` -- rejected: the comparison that decides "is this the pin we committed to" gets one author, which is the whole point of the guard; its message's "row embedded under X" reads correctly here as "the vectors this driver produces would be embedded under X". (c) Skip non-retrievable rows silently instead of raising when one is returned -- rejected: a repository whose predicate silently lost a conjunct would then work forever, invisibly; raising costs one sweep and leaves every row exactly as it was. (d) Mirror `stores.pg.search`'s full retrievability predicate including the Tier-A/`candidate` rule and the `pinned` exclusion -- rejected as (2) explains; a superset is wasted spend, a divergent copy is a governance bug.
**Rationale:** The chunk's own tests were mutation-tested (14 mutations, every one goes red), and two of them exposed the gap this entry closes: the pin-change test constructed a v2 pin against a still-v1 driver -- the exact silent swap -- and passed, and a `finished_at = started_at` mutation passed every timestamp assertion. Both are fixed: the driver/pin guard makes the first *unconstructible* rather than merely tested against, and the fake port now advances the injected clock inside `embed()` so the two timestamp reads are distinguishable. The wider principle is the one `stores.pg.search`'s own docstring states for its read side and this module now applies to the write side: the query predicate is the control, the assertion on the returned rows proves the control held, and a quarantined row that never receives a vector is protected by the data rather than by the text of somebody else's WHERE clause.

## D-125 The shadow-confirmation append is three-valued, the growth cap and the project wall hold across a whole sweep, and the writer takes no clock because there is nothing to timestamp
**Decision:** Three corrections to `workers/corroboration.py` as first written (D-121), each found by mutating the module and watching its tests stay green. (1) `CorroborationRepoPort.append_confirming_run` returns a three-valued `AppendOutcome` (`APPENDED` / `ALREADY_PRESENT` / `ROW_NOT_ELIGIBLE`), not a `bool`. The eligibility predicate (`status = 'quarantined'`, `project_id = ...`) must live in the SAME statement as the array append or the append is not atomic, so a row archived by the quarantine-TTL sweep between this worker's select and its update produces exactly zero updated rows -- indistinguishable, in a row count, from an already-present run. Folded into `False`, that made `record_one` return `recorded=True` for a memory that had left quarantine and received nothing. The documented statement is correspondingly rewritten as a `FOR NO KEY UPDATE` CTE that reports all three answers, rather than a bare `UPDATE ... WHERE NOT (run_id = ANY(...))` whose zero-row case is ambiguous and whose "the guard is re-evaluated after the lock" behaviour is READ COMMITTED-specific (under REPEATABLE READ the same statement raises a serialization failure instead of quietly reporting the run already present). (2) `run_once` advances its per-row snapshot as it writes. `record_one` is a pure function of the snapshot it is handed, so re-handing it the pre-batch snapshot for every offered run made both snapshot-derived guards vacuous for the whole batch: measured, a candidate source offering 1,000 runs for a row holding none appended 999 of them despite a `MAX_CONFIRMATIONS_CONSIDERED` (256) cap, and the same run offered three times cost three round trips. The cap and distinctness are properties of the COLUMN (PLAN.md §5: "distinct confirming run_ids"), so they hold per row per sweep, not per call. The snapshot advances ONLY on `recorded`, never on a refusal -- advancing on a refused append would make the next offer of that run hit the "already present" fast path and report a write that never happened. (3) `run_once` applies `_require_row` to every row the select returned BEFORE calling `CorroborationCandidateSource.candidate_runs` for any of them. That port is host-supplied third-party code; a store predicate that has stopped holding would otherwise disclose another project's row and its provenance to it (invariant 4) with no append required, and would do so only after this worker had already written to the rows preceding it in the batch. Separately, `CorroborationWriter` no longer takes a `Clock` and `append_confirming_run` no longer takes `now`.
**Context:** The module shipped with 16 tests, all passing. Mutation testing showed two of them could not fail from any change to the module (`test_run_once_skips_rows_that_have_already_left_quarantine` asserted only that the in-file fake's own `select_quarantined` filtered on status; the growth-cap test pinned no boundary, so rewriting the guard as `>= MAX_CONFIRMATIONS_CONSIDERED - 1` passed the whole file), and that `now = self._clock.now()` could be replaced with a hardcoded constant with no test failing -- `memory_item` has no `updated_at`, `shadow_confirm_runs` is a bare `uuid[]` with no room for a per-element timestamp, and the prescribed UPDATE therefore had no column to write the value to. PLAN.md §5's "every Q update and shadow confirmation records `epoch_id`" is satisfied one level up by `workers.shadow_validator.ShadowTransitionWrite.epoch_id`, on the transition this evidence eventually justifies.
**Alternatives considered:** (a) Keep the `bool` return and have implementations raise on an ineligible row -- rejected: a concurrent quarantine-TTL sweep is ordinary operation, not a fault, and an exception would abort the rest of the batch over it; the caller needs a refusal it can report, which is what `CorroborationOutcome.reason` already is. (b) Keep `now`/`Clock` and document that implementations may stamp it on an audit record -- rejected on this tree's own precedent: D-122 alternative (c) rejects "a parameter the SQL never reads" as "a plausible-constant return by another name", and `AuditSinkPort` has zero implementations and no table (audit finding M11), so the consumer is hypothetical. The real gap -- that the DDL cannot say WHEN a run was recorded against a memory, or under which judge pin -- is named here instead of hidden behind a parameter. (c) Re-read each row from the repo inside `record_one` instead of trusting the caller's projection, so a fabricated `provenance` could not get a run id into the array -- rejected: it doubles the I/O of every sweep to harden a check that is already the first of three, the last of which (`workers.shadow_validator._resolve_confirmations` subtracting `origin_runs` from the row's own stored provenance) is the authoritative one and cannot be bypassed by anything this writer records. (d) Enforce the growth cap only in SQL -- rejected: the bound belongs beside the reason for it (`domain.state_machine.MAX_CONFIRMATIONS_CONSIDERED`, reused not re-declared), and a store implementation does not exist yet, so SQL-only would mean unbounded today.
**Rationale:** All three defects have the same shape: a control that is correct for one call and absent for the sequence of calls a deployment actually makes. The cap, the distinctness of `shadow_confirm_runs`, and the project wall are properties of a ROW over a SWEEP, and each was being checked against a value frozen before the sweep began -- which is exactly the "the rules were built with unusual fidelity and the runtime was not" finding this remediation exists to close, reproduced in miniature inside a module written to close it. Every fix is pinned by a test that fails when the fix is reverted: reverting the snapshot advance, the up-front project check, the three-valued outcome, the refusal-does-not-advance rule, or either direction of the cap boundary each turns the file red.

## D-126 Benjamini-Hochberg is computed once, in exact arithmetic, because the two implementations it replaces disagreed with each other; the SQL scope predicate is opt-in, because applying it with nothing bound is a retrieval outage, not a narrowing
**Decision:** Supersedes D-122 on both of its halves; D-122's file list, its identity-alias arrangement for `api.reports._bh_adjusted_p_values`, and its `_scope_fragment`/`assert_never` derivation of the predicate from `domain.enums.ScopeType` all stand.
(1) `workers/statistics.py` computes the step-up adjustment in `fractions.Fraction` (`_exact_adjusted`), and the two public shapes are two readings of that one exact result: `bh_adjusted_p_values` returns `float(exact)` (the dashboard q-value), `benjamini_hochberg` compares the exact value to `alpha` (the kill-switch boolean). Both validate every p-value into `[0, 1]`, which is a tightening on the numeric shape -- the function it replaces validated nothing, and `Fraction(nan)` fails inside the arithmetic rather than at the caller's value.
(2) `stores/pg/search.py`'s `lexical_arm` applies `_SCOPE_PREDICATE` only when the caller supplies a `RunVisibility`. With none supplied it issues the statement it shipped before this entry, byte-identical apart from being generated from the same template; `vector_arm` carries no scope conjunct at all. `_scope_predicate_params` therefore takes a non-optional `RunVisibility` -- there is no "absent visibility" case for it to encode, only unresolved references, which still bind SQL `NULL` and still fail closed exactly as `domain.visibility.scope_visible`'s `is not None` guards do.
**Context:** D-122 asserted its extracted `benjamini_hochberg` was "byte-identical in behaviour to `workers.killswitch.benjamini_hochberg`'s current standalone definition, verified against it on 20,000 randomised trials." That is false, and a randomised differential weighted onto rank boundaries shows it: the two disagree on roughly 4,500 of 200,000 inputs. `p <= (rank/m)*alpha` (killswitch) rounds the THRESHOLD up and fires spuriously -- e.g. `p = (0.03, 0.729, (1/5)*0.05, 0.548, 0.93)` at `alpha = 0.05`, where the exact answer rejects nothing and killswitch rejects one cell. `min(1, p*m/rank) <= alpha` (the extracted copy) rounds the STATISTIC up and misses -- e.g. `p = (0.1, 0.1, 0.1)` at `alpha = 0.1`, where the exact answer rejects all three and it rejects none. Neither original was right; each is a different rounding of one exact inequality, so no choice between them and no adjustment to either `<=` fixes it. Separately, D-122's second half applied the scope predicate unconditionally with every resolver bound to `NULL`, on the stated reasoning that "a caller seeing FEWER retrievable ids than before is a missed candidate, not a leak." On this corpus it is neither: `workers/extractors/base.py:623` and `workers/distiller.py:794` both hard-code `scope_type=ScopeType.AGENT_TYPE`, so essentially every retrievable row in a deployed Tracebed is agent-type scoped, `hotpath.retriever.Retriever.retrieve()` has no `RunVisibility` to pass (it takes only `project_id`, `query_text`, `cfg`), and both arms would have matched `project_shared` rows only -- returning nothing for every query, while `scope_visible` and the assembler would have accepted exactly the rows the SQL dropped. No offline test could see it: a fake cursor does not evaluate `WHERE`.
**Alternatives considered:** (a) Keep the float step-up and make `workers/killswitch.py`'s copy match it verbatim when the import swap lands -- rejected: that standardises on the false-negative rounding, i.e. on a kill switch that fails to fire when every cell's p-value equals alpha exactly. (b) Define the boolean off the ROUNDED q-value so the displayed number and the verdict always agree -- rejected: that is alternative (a) by another route; the ordering `float(exact) < alpha => exact <= alpha` and `float(exact) > alpha => exact > alpha` means the two shapes can only ever appear to disagree at `float(exact) == alpha`, in the conservative direction, which is a display artefact of one double and is pinned as a theorem in `tests/phase3/test_bh_single_authority.py` rather than traded for a wrong trigger. (c) Use `decimal` or a tolerance instead of `Fraction` -- rejected: a tolerance is a fifth arbitrary constant governing a governance decision (hard rule 4), and `Decimal` is not exact over binary float inputs either; `Fraction` is exact over exactly the inputs this function has (floats are dyadic rationals; `m` and `rank` are integers). Cost is irrelevant here -- both callers correct one hypothesis per grid cell, off the hot path. (d) Keep D-122's unconditional scope predicate and accept the narrowing -- rejected: it is not a narrowing of a leak, it is the memory system returning nothing, and it drops rows the assembler would keep, which inverts the direction the task's own instruction calls safe. (e) Make `visibility` a required parameter of `lexical_arm` so the outage is impossible -- rejected: `hotpath/retriever.py` is outside this chunk's file list and its positional call would break, regressing baseline. (f) Stash a per-request `RunVisibility` on the `SearchStore` instance so `vector_arm` could read one without changing its signature -- rejected outright: one `SearchStore` serves every concurrent request in the process, so per-request state on it is a cross-tenant race.
**Rationale:** Both halves of D-122 failed the same way: a control was declared, and the declaration was not checked against what the control actually does. The BH claim was checked by seven hand-picked p-value tables, none of which sits on a rank boundary -- the only region where a wrong implementation of this procedure differs from a right one -- so a differential test between two genuinely disagreeing implementations passed. The scope claim was checked by substring assertions plus a hand-written scope-type-to-parameter-name table in the test, which stays consistent with itself no matter what the SQL binds: swapping `%(visible_user_scope_id)s` for `%(visible_workflow_template_id)s` in `_scope_fragment`'s `user` branch -- a cross-user exposure -- leaves every one of those assertions green, verified by running them against exactly that mutation. Both are now checked against an INDEPENDENT statement of the same rule: `_classic_reject_exact` implements the other standard formulation of Benjamini-Hochberg in exact arithmetic and is differential-tested over 20,000 boundary-weighted inputs, and `_evaluate` implements the restricted SQL grammar `_SCOPE_PREDICATE` is written in and runs the generated predicate text against real rows with real bindings, comparing every verdict to `domain.visibility.scope_visible`. CONTRACT GAPS, both narrowed to one edit each and both now measured rather than asserted: `workers/killswitch.py` should import `benjamini_hochberg` from `workers.statistics` and delete its local copy -- a behaviour change that removes the spurious boundary triggers, with the exact inputs listed in the test file; and `hotpath/retriever.py`'s `retrieve()` should take a `RunVisibility` (its caller `hotpath/pipeline.py` already holds a `ProjectScope` carrying the mandatory `agent_type_id`) and forward it to `lexical_arm`, at which point the SQL-side control becomes live. Until then D-097's assembler filter remains the scope control, which is exactly the audited status quo -- no worse, and no pretence otherwise. ## D-129 A project-wide killswitch overlay row now matches alongside an agent-type-specific one, and either row saying DISABLE wins
**Decision:** `Repo.get_killswitch_overlay`'s predicate changes from `agent_type_id IS NOT DISTINCT FROM %(agent_type_id)s` to `agent_type_id IS NULL OR agent_type_id = %(agent_type_id)s`. The old form only ever matched ONE of the two rows a `mem_type` can have (migrations/0001:127-141's project-wide `agent_type_id IS NULL` row, and an agent-type-specific row): `ConfigResolver.effective` always calls this with a resolved, non-NULL `agent_type_id`, and `NULL IS NOT DISTINCT FROM <uuid>` is false, so the project-wide row could never be selected by any caller that exists in this codebase. A project-wide DISABLE therefore did nothing -- memory kept being injected for every agent type -- while `list_killswitch_state` / `GET /admin/killswitch_state` kept reporting it as active, the worst shape a safety control can have. Precedence, when both a project-wide row and an agent-type row exist for the same `mem_type`: the merge is a logical OR of their `disabled` flags, computed in Python after the fetch (no `agent_type_id` needed in the merge itself, since OR does not need to know which row said so). A project-wide DISABLE overrides an agent-type ENABLE -- the project-wide row is the bigger hammer, and an operator reaching for it is stating an intent about the whole project. Symmetrically, an agent-type-specific DISABLE is never silently re-enabled by the project-wide row defaulting the same `mem_type` back to enabled elsewhere: disabling is always the safer direction for a memory-injection control, so whichever row asserts it is authoritative, not just the project-wide one.
**Context:** Found by BMAD-METHOD v6.10.0's review skills (`docs/BMAD-EVALUATION.md`) against `domain/config.py:765` and migrations/0001; confirmed here by reading `ConfigResolver.effective` (calls `get_killswitch_overlay(project_id, agent_type_id)` exactly once per resolution, with `agent_type_id` already resolved by that point) and `hotpath/assembly.py:176` (`cfg.killswitch_overlay.get(mem_type.value, False)` -- absence means enabled, so a dropped project-wide row fails OPEN, not closed).
**Alternatives considered:** (a) "The more specific row wins" (agent-type row, if present, decides; project-wide only fills gaps) -- rejected: that lets a project-wide DISABLE be silently overridden by a stale agent-type ENABLE row, which is the exact failure this entry exists to close, and there is no operational reason an agent-type override should outrank the bigger hammer. (b) "The project-wide row, if present, always decides regardless of value" (project-wide ENABLE would then override an agent-type DISABLE too) -- rejected: that direction is less safe than today's already-broken behaviour in one respect -- it would let a general project-wide re-enable silently undo a targeted, deliberate agent-type disablement, which is the "disabled in effect, enabled in the UI" failure mode in reverse. (c) Two separate store calls (one for the NULL row, one for the agent-type row) composed by the caller -- rejected: `ConfigStorePort.get_killswitch_overlay`'s signature is fixed by contract §3.4 and is not this chunk's file to change; one query with an OR precedence resolved inside `Repo` keeps the port's shape and fixes the query behind it. (d) Select `agent_type_id` too and resolve precedence by explicit rank rather than OR -- rejected: OR already produces the exact required ordering for both directions (project-wide disable beats agent-type enable, and vice versa) with no extra column and no ambiguity about which row "wins" when both say the same thing.
**Rationale:** A kill switch that reports itself as applied while doing nothing is worse than no kill switch, because an operator who checks the admin surface and sees it active stops looking for another way to stop the behaviour. The fix is pinned by a mutation check (`tests/phase3/test_killswitch_overlay_scope.py::test_reverting_to_the_old_predicate_fails_the_project_wide_scenario`) that runs the literal old predicate text against the same canned fixture and shows it drops the project-wide row -- proof that the old form really did pass the whole existing suite, not an asserted claim about it.

## D-135 `trace_index.input_signature_hash` gets a ONE-WAY sentinel upgrade, not first-write-wins; `agent_type_id` joins the pinned identity columns (supersedes D-130 in part)
**Decision:** D-130 applied `COALESCE(trace_index.<col>, EXCLUDED.<col>)` to BOTH `submitter_principal` and `input_signature_hash`, and argued the `EXCLUDED` arm "never fires, since both columns are `NOT NULL` from the very first insert". **Alternatives considered:** (a) A boolean-match `restrict-to-matching` lexical arm mirroring the phantom `@@@` — impossible: vchord_bm25 0.3.0 has only the `<&>` scoring operator; top-k-by-score with abstention as the filter is the correct parallel to the ANN arm. (b) Bind the PARENT partitioned bm25 index to `to_bm25query` — rejected: it is storage-less and errors at execution; the per-partition index is both the only working choice and the correct per-project IDF source. (c) Set `bm25_catalog` on the path via `ALTER DATABASE`/globally — rejected: a transaction-scoped `SET LOCAL` on the read path alone cannot change name resolution for `Repo` writes or other queries and never leaks onto a pooled connection. (d) Compute document frequency from the ranking surface — impossible: vchord_bm25 exposes no term-stat function, which is precisely why DF comes from the tsvector. (e) A bert-only (no-stemming) tokenizer — deferred: porter2 stemming keeps the ranking arm's tokenization the same shape as the 'english' DF source; if IDF granularity needs tuning it is a tokenizer-definition change in 0005 with no code change. (f) Edit shipped migration 0002 to add the column — rejected per the append-only migration convention; a new 0005 that a disposable-dev reset re-applies cleanly is the mechanism.
**Rationale:** Ranking and DF were deliberately split by D-003 (BM25 for ranking, an exact per-term DF for the rarity gate), and vchord_bm25's lack of a df accessor makes that split structural rather than stylistic: the ranking column and the tsvector serve two different roles and are allowed to tokenize marginally differently (both are English snowball-family stemmers). The negate+`GREATEST(0.0::real, ...)` transform enforces abstention's ≥0/finite invariant at the SQL boundary (a no-op on real data, since `<&> ≤ 0` always, but a guaranteed guard against any float edge). Every claim was checked against the live DB: the default-search_path `bm25vector` failure, the negative-for-better sign, the parent-index `UndefinedFile`, and the exact DF counts (`retry`→2, `budget`→1, `xyzzy`→0 with the zero-match term still present via the LEFT JOIN) were each observed directly.
